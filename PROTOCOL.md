# Autoterm / Planar Heater Control Protocol

**Version:** 0.3  
**Status:** Reverse-engineered, partly validated by real RX capture, intentionally incomplete  
**Primary sources:** Working Node-RED flow `20220918_NodeRed_Flow.json` and
the real captures in `captures/2026-08-09-heater-off-status.md` and
`captures/2026-08-09-heater-init-response.md`

## 1. Scope and confidence model

This document describes the serial protocol behavior that is demonstrably used by the working Node-RED heater controller.

It is not claimed to be an official Autoterm protocol specification.

Confidence labels:

- **VERIFIED** — explicitly present in the working Node-RED flow or observed
  in a real heater capture; capture-specific verification is labelled as such
- **DERIVED** — strongly inferred from the implementation
- **UNKNOWN** — not established by the current source

Migration code must reproduce VERIFIED behavior before attempting improvements.

## 3. UART configuration

The Node-RED heater serial port uses:

| Parameter | Value |
|---|---|
| Baud rate | 9600 |
| Data bits | 8 |
| Parity | None |
| Stop bits | 1 |
| Flow control | None |
| Mode | Binary |

Notation:

`9600 8N1`

Node-RED also uses an approximately 200 ms inter-byte receive delimiter and a 10 s response timeout.

The 200 ms value is a property of the existing Node-RED framing configuration, not proven to be a formal protocol requirement.

**Confidence:** VERIFIED.

## 4. General frame layout

Outgoing frames generated by the working implementation follow:

```text
Byte 0    0xAA
Byte 1    device/source identifier
Byte 2    payload length
Byte 3    reserved/unknown (TX currently 0x00)
Byte 4    command
Byte 5..  command payload
Last 2    CRC16
```

Conceptually:

```text
+------+--------+--------+----------+---------+------------+---------+
| 0xAA | Device | Length | Reserved | Command | Payload... | CRC16   |
+------+--------+--------+----------+---------+------------+---------+
```

For known TX frames, total length is:

`7 + payload_length`

The 2026-08-09 real status and initialization responses use the same layout:

- status: `19 + 7 = 26` bytes
- initialization: `5 + 7 = 12` bytes

This confirms the rule for commands `0x0F` and `0x04`; other RX response types
still require captures.

**Confidence:** TX layout VERIFIED; status and initialization RX layouts
VERIFIED by capture; generic RX layout otherwise DERIVED.

## 5. Start marker

All known controller-generated frames start with:

`0xAA`

The real status and initialization responses both begin with `0xAA`.
Universal use by every RX command is not yet independently proven.

**Confidence:** TX VERIFIED; status and initialization RX VERIFIED by capture;
other RX commands remain DERIVED.

## 6. Device/source byte

Controller-generated frames use:

`byte[1] = 0x03`

The receive path only accepts heater messages where:

`byte[1] = 0x04`

Strongly inferred mapping:

- `0x03` — control panel / replacement controller
- `0x04` — heater

The real status and initialization responses both have `byte[1] = 0x04`,
confirming the heater source identifier for commands `0x0F` and `0x04`.

**Confidence:** controller TX VERIFIED; heater identifier VERIFIED for status
and initialization RX and otherwise DERIVED with high confidence.

## 7. Payload length

`byte[2]` is used as the count of command-payload bytes.

Examples:

No payload:

```text
AA 03 00 00 04
      ^^
      0 payload bytes
```

One payload byte:

```text
AA 03 01 00 11 14
      ^^       ^^
      1        payload
```

Six payload bytes:

```text
AA 03 06 00 01 FF FF 02 14 01 03
      ^^       <---------------->
      6              6 bytes
```

Real status RX example:

```text
AA 04 13 00 0F ... 6D A0
      ^^
      19 payload bytes; 26 bytes total
```

Real initialization RX example:

```text
AA 04 05 00 04 12 8A 00 3D D6 CB A6
      ^^
      5 payload bytes; 12 bytes total
```

**Confidence:** VERIFIED for TX and for the captured status and initialization
RX frames; not yet verified for every RX command.

## 8. Reserved byte

`byte[3]` is always transmitted as:

`0x00`

Its semantic meaning is unknown.

Do not invent a meaning in code.

Recommended behavior:

- TX → send `0x00`
- RX → preserve/log whatever value is received

The captured status and initialization responses both contain `0x00` at byte
3.

**Confidence:** TX value VERIFIED; RX value observed for status and
initialization; semantics and universal RX value UNKNOWN.

## 10. CRC algorithm

The Node-RED flow implements a table-driven reflected CRC using:

- Initial CRC: `0xFFFF`
- Reflected polynomial representation: `0xA001`
- Final XOR: none
- CRC calculated over all bytes before the CRC itself

Equivalent bitwise algorithm:

```python
def crc16(data):
    crc = 0xFFFF

    for byte in data:
        crc ^= byte

        for _ in range(8):
            if crc & 1:
                crc = (crc >> 1) ^ 0xA001
            else:
                crc >>= 1

    return crc & 0xFFFF
```

This is algorithmically in the CRC-16/IBM/MODBUS family, but wire byte order must follow the existing implementation rather than generic Modbus assumptions.

The real status and initialization responses independently produce the same
calculated CRC as their received trailing values.

**Confidence:** VERIFIED from the TX implementation and independently matched
by the captured status and initialization RX CRCs.

## 11. CRC serialization

The Node-RED flow converts the numeric CRC to a hex string and appends those bytes directly.

For a numeric CRC such as:

`0x9F3D`

the transmitted bytes are:

`9F 3D`

Therefore known TX behavior is:

**CRC high byte first, then low byte.**

This differs from the usual Modbus RTU wire order.

The MicroPython implementation must initially reproduce this exact behavior.

The captured status response contains numeric CRC `0x6DA0` serialized as
`6D A0`; the initialization response contains `0xCBA6` serialized as `CB A6`.
Together they independently confirm the same byte order for commands `0x0F`
and `0x04` RX.

**Confidence:** TX VERIFIED from implementation; status and initialization RX
VERIFIED by capture.

### 11.1 Existing Node-RED edge case

The existing JavaScript converts `crc.toString(16)` without explicit 4-digit zero padding.

A CRC value with leading zero digits could theoretically be serialized incorrectly.

Do not reproduce this accidental string-formatting weakness.

Instead serialize the 16-bit value explicitly as two bytes:

```python
crc_hi = (crc >> 8) & 0xFF
crc_lo = crc & 0xFF
```

This preserves the intended high-byte-first wire format.

## 13. Initialization — command `0x04`

Controller base frame:

```text
AA 03 00 00 04
```

Complete known TX frame:

```text
AA 03 00 00 04 9F 3D
```

The Node-RED controller initializes its internal flag to false.

A 1-second heartbeat checks initialization.

While not initialized, the controller repeatedly sends the initialization command.

The flow marks initialization complete when it receives a heater-originated message with:

- byte 1 = `0x04`
- command byte 4 = `0x04`

The existing flow does not validate incoming CRC before accepting this response.

The real initialization response captured on 2026-08-09 is:

```text
AA 04 05 00 04 12 8A 00 3D D6 CB A6
```

It contains five payload bytes, `12 8A 00 3D D6`. Their semantics and whether
they vary by heater model, firmware, or configuration are unknown. The
captured CRC `CB A6` is valid.

**Confidence:** request and receive handling VERIFIED in the flow; response
layout and CRC VERIFIED by real capture; payload semantics UNKNOWN.

## 14. Status request — command `0x0F`

Once initialized, the one-second heartbeat sends:

```text
AA 03 00 00 0F 58 7C
```

The receive path recognizes status responses where:

- byte 1 = `0x04`
- byte 4 = `0x0F`

The first real capture contains 22 observations of this identical status
response:

```text
AA 04 13 00 0F 00 01 00 1E 7F 00 80 01 2F 00 00 00 00 00 00 00 00 00 60 6D A0
```

**Confidence:** VERIFIED in the flow and by real status RX capture.

## 15. Status response fields currently used

The Node-RED flow extracts the following absolute byte positions:

| Absolute index | Current meaning | Conversion |
|---|---|---|
| 11 | Heater voltage | raw / 10.0 = volts |
| 13 | Glow plug raw value | no conversion documented |
| 14 | Heater state | mapped enum |
| 19 | Vent/fan raw value | no conversion documented |

Example:

`frame[11] = 126` → `12.6 V`

The real status capture decodes under the same existing rules as:

- `frame[11] = 128` → `12.8 V`
- `frame[13] = 47` → glow-plug raw value `47`
- `frame[14] = 0` → reported state `Heater Off`
- `frame[19] = 0` → fan raw value `0`

These are real raw values. The user independently confirmed that the heater
was physically off during the capture, supporting the `0 = Heater Off`
mapping. The reported supply voltage was not independently measured, so the
capture still confirms a parser vector rather than every field's scaling.

No complete status-response payload map can be derived from the current flow because the remaining bytes are not interpreted.

**Confidence:** byte positions VERIFIED; other semantics UNKNOWN.

## 19. Start — Power mode

The Node-RED application-level Power mode is represented internally as `"04"`.

Generated protocol payload:

```text
FF FF 04 FF 01 PP
```

Complete frame before CRC:

```text
AA 03 06 00 01 FF FF 04 FF 01 PP
```

Where:

`PP` = power level 1–9

Known current interpretation:

| Payload offset | Value | Interpretation |
|---|---|---|
| 0 | `FF` | unknown |
| 1 | `FF` | unknown |
| 2 | `04` | power-control mode |
| 3 | `FF` | target temperature irrelevant |
| 4 | `01` | comment indicates ventilation/fan on |
| 5 | `01–09` | requested power level |

Exact semantics of offsets 0, 1 and possibly 4 are not independently verified.

**Confidence:** frame construction VERIFIED; some semantics DERIVED/UNKNOWN.

## 20. Start — Temperature mode

The application has two distinct user modes:

- `21` — Roof Tent
- `22` — Cabin

These are application-level choices only.

Both map to heater start mode:

`0x02`

Generated payload:

```text
FF FF 02 TT 01 03
```

Complete frame before CRC:

```text
AA 03 06 00 01 FF FF 02 TT 01 03
```

Where:

`TT` = target temperature as one byte

Example target 20 °C:

`TT = 0x14`

Complete test frame:

```text
AA 03 06 00 01 FF FF 02 14 01 03 67 EE
```

Known current interpretation:

| Payload offset | Value | Interpretation |
|---|---|---|
| 0 | `FF` | unknown |
| 1 | `FF` | unknown |
| 2 | `02` | heater temperature-control mode |
| 3 | `TT` | target temperature |
| 4 | `01` | comment indicates ventilation/fan on |
| 5 | `03` | hard-coded value; exact meaning unknown |

The Node-RED comment notes that the final `03` is hard-coded and may be changed by the heater.

**Confidence:** frame VERIFIED; some field semantics UNKNOWN.

## 21. Application vs. protocol modes

Keep these concepts separate.

Application modes:

```text
POWER
ROOF_TENT_TEMPERATURE
CABIN_TEMPERATURE
```

Historical Node-RED values:

```text
04 = Power
21 = Roof Tent
22 = Cabin
```

Heater protocol start-mode values observed:

```text
04 = Power mode
02 = Temperature mode
```

Both Roof Tent and Cabin therefore map to the same Autoterm protocol mode and only differ in which external DS18B20 reading is reported.

## 22. External temperature report — command `0x11`

Base frame:

```text
AA 03 01 00 11 TT
```

Where:

`TT` = current external temperature encoded as one byte

Example 20 °C:

```text
AA 03 01 00 11 14 B2 51
```

The Node-RED implementation uses:

`Math.ceil(sensor_temperature)`

before sending.

Therefore:

- 19.1 °C → 20
- 19.9 °C → 20

It is not known whether ceiling rather than normal rounding is required by the heater protocol.

Initially preserve this behavior or make the conversion explicit and testable.

**Confidence:** VERIFIED implementation behavior; protocol necessity UNKNOWN.

## 23. External-temperature reporting cadence

The Node-RED control cycle uses a one-second heartbeat.

When initialized it:

1. sends a Status request
2. delays approximately 200 ms
3. evaluates the latest known heater state
4. for relevant active temperature-control states, sends the selected external temperature
5. separately evaluates requested Start/Stop actions

External temperature is therefore effectively sent approximately once per second while the application is in the supported active temperature modes/states.

The current flow routes temperature reporting for heater states:

- Starting
- Running
- Shutting Down

The `Temp Monitoring (6)` branch does not currently route to temperature transmission.

This should be treated as existing behavior, not proof that state 6 must never receive temperature updates.

**Confidence:** VERIFIED Node-RED behavior.

## 24. Main communication cycle

Simplified existing behavior:

```text
Every 1 second
    |
    +-- initialized? no --> send INIT
    |
    +-- initialized? yes -> send STATUS
                              |
                              ~200 ms
                              |
                         evaluate state
                              |
                    +---------+---------+
                    |         |         |
                 temp?      start?     stop?
```

The ESP32 implementation does not need to reproduce Node-RED node timing internally, but initial compatibility testing should preserve behavior closely enough to avoid introducing multiple unknown changes at once.

## 25. Receive filtering

The existing receive path:

1. filters on `payload[1] == 0x04`
2. examines command at `payload[4]`

Recognized command values:

- `0x01`
- `0x02`
- `0x03`
- `0x04`
- `0x0F`
- `0x11`

Only Initialization and Status currently have meaningful receive-side handling.

**Confidence:** VERIFIED.

## 26. Incoming CRC validation

The current Node-RED flow does not validate CRC on received frames.

This is an implementation gap, not evidence that RX frames lack CRC.

The real status response ends in `6D A0`; calculation over its preceding 24
bytes yields `0x6DA0`. The real initialization response ends in `CB A6`;
calculation over its preceding 10 bytes yields `0xCBA6`. This confirms for
commands `0x0F` and `0x04` that RX uses:

- the same CRC algorithm as TX
- a trailing two-byte CRC
- high-byte-first serialization

The ESP32 should still:

- preserve complete raw RX frames
- calculate expected CRC where the assumed frame layout allows it
- report CRC result in diagnostics
- avoid making aggressive assumptions for response types not yet captured

The global strict-framing mode remains opt-in because unknown response types
must still be preserved rather than discarded. A later HeaterController shall,
however, require `crc_valid=True` before using captured initialization or
status frames for state transitions.

## 27. Recommended RX frame-length rule

Based on known TX construction:

```text
expected_length = payload_length + 7
```

Where `payload_length = frame[2]`.

The 26-byte real status response has `frame[2] = 19`; the 12-byte real
initialization response has `frame[2] = 5`. This rule is therefore VERIFIED for
commands `0x0F` and `0x04`. It remains DERIVED for other RX commands until
captured.

## 28. Recommended parser behavior

Conceptual parser:

```python
find 0xAA
read fixed header
payload_length = frame[2]
expected_length = payload_length + 7
wait for expected length
validate structure
calculate/report CRC
preserve raw frame
decode known fields
```

Requirements:

- handle partial frames
- handle multiple back-to-back frames
- recover from junk bytes
- preserve unknown commands/fields
- avoid blocking the event loop

## 30. Open protocol questions

The Node-RED source and the real status/initialization captures still do not
establish:

### Framing

1. official meaning of byte 3
2. whether every heater response type starts with `0xAA` (confirmed for status and initialization)
3. whether byte 2 always means exactly payload length on RX (confirmed for status and initialization)
4. whether framing ever uses escaping
5. whether multiple responses can arrive back-to-back without a gap

### RX CRC

6. whether every RX response type uses exactly the same CRC (confirmed for status and initialization)
7. whether every RX response type serializes CRC high-byte first (confirmed for status and initialization)
8. exact RX CRC field location for every message type (trailing for status and initialization)

### Initialization

9. meaning of the captured five-byte Initialization payload `12 8A 00 3D D6`
10. whether the payload varies with heater model/version/configuration

### Start payload

11. meaning of the first two `FF` bytes
12. exact meaning of `01` in payload offset 4
13. exact meaning of fixed `03` in temperature mode
14. other possible operating modes

### Status

15. meanings of all ignored status bytes
16. glow-plug raw-value mapping
17. fan/vent raw-value mapping
18. location/encoding of heater fault codes
19. whether pump frequency, internal temperature or flame state are present

### External temperature

20. required report interval
21. allowed full temperature range
22. negative-temperature encoding
23. whether `ceil()` is required
24. whether state 6 should receive external-temperature reports

## 31. Protocol-capture strategy for future versions

The recovered real captures now include the repeated heater-status frame and
one initialization response, documented under `captures/`. The ESP32 shall
still include first-class protocol capture for additional states and response
types.

For each frame record:

- monotonic timestamp
- local wall-clock timestamp when available
- RX/TX
- raw hex
- length
- command
- parsed known fields
- CRC result
- application/heater state context

Recommended captures:

- repeated init and later cold-boot comparison
- heater OFF status
- start Power 1
- start Power 5
- start Power 9
- target 10 °C
- target 20 °C
- target 30 °C
- Starting → Running lifecycle
- shutdown lifecycle
- Temp Monitoring state
- sensor temperatures across several values

Future `PROTOCOL.md` revisions can then upgrade DERIVED/UNKNOWN fields to VERIFIED.
